# 0.12.0 设计：把“像 API”推进到对象/语义层

日期：2026-11-16
版本：0.12.0
状态：已实现并部署

## 目标

0.11.0 解决了“网页端看得到、API 端看不到”的产物与引用问题。0.12.0 继续按
OpenAI 的真实对象面与参数语义收敛，重点是那些**形状不对、字段缺失、参数被静默忽略**
的地方：`/v1/videos` 仍是自定义任务形状、`usage` 是按字符估算、Stored Chat Completions
缺失、Responses 对象缺字段、`previous_response_id` 的 instructions 语义错误、
Files 缺过期/分页、Images/Models 缺字段。

原则不变：

1. 能由上游真实兑现的能力，按 OpenAI 形状实现。
2. 上游物理上做不到的能力，明确 400/501，不静默忽略、不伪造。
3. 每个修复都有单元测试；发布前跑全量测试与真实账号 E2E。

## 外部审计结论（Explore）

审计覆盖 Chat / Responses / Images / Videos / Files / Models 六个面，确认的差异：

| 面 | 差异 | 级别 |
|---|---|---|
| Videos | `/v1/videos` 返回自定义 task 形状，缺 Sora 的 multipart、`/content`、`/remix`、分页、状态映射 | P0 |
| Chat | `store` 参数被忽略；`usage` 为 `len//4`；chunk 缺 `service_tier`/`logprobs`；音频被静默忽略 | P0/P1 |
| Chat | Stored Completions 的 list/retrieve/update/delete/messages 全部缺失 | P0 |
| Responses | 对象缺 `completed_at`/`service_tier`/`access_programs`/`background`/`usage details` 等；`input_items` 默认顺序错误 | P1 |
| Responses | `previous_response_id` 只在“本轮带 instructions”时才剔除旧 system；`background` 被静默忽略 | P1 |
| Files | 缺 `expires_after`、分页游标、`purpose` 校验 | P1 |
| Images | 响应缺 `background`/`output_format`/`size`/`quality`；`stream` 被静默忽略 | P1 |
| Models | 缺 `shutdown_date` | P2 |

## 关键决策

### 1. Videos：采用 Sora 形状，不再暴露内部 task

- `POST /v1/videos` 同时接受 JSON 与 multipart；`image`/`input_reference` 支持 data URL、
  http(s)、base64、`file_id`、上传文件。
- 状态机映射：内部 `queued/running/succeeded/failed` → `queued/in_progress/completed/failed`；
  `completed_at`/`expires_at`/`progress`/`remixed_from_video_id` 按 Sora 字段返回。
- `GET /v1/videos` 分页带 `first_id`/`last_id`/`has_more`，`after` 游标按创建时间。
- `/content` 只接受 `variant=video`；`edits`/`extensions`/`characters` 返回 501。
- 仍保留内部 task 作为实现细节；公开 id 为 `video_<hex>`（Sora 形状），旧
  `task_<hex>` id 仍可解析；媒体文件与任务一起删除。

### 2. Chat：Stored Completions 真正落盘

- 只有显式 `store: true` 才保存（OpenAI 的 Chat `store` 默认就是 `false`）。
- `data/chat_completions.json` 保存完整 ChatCompletion 对象 + 请求输入消息；
  输入消息按 `ChatCompletionStoreMessage` 形状返回：`id = "{completion_id}-{i}"`、
  `role`、`content`（文本拼接）、`name`、`content_parts`（多模态原样保留）。
- 消息端点返回的是**输入消息**；生成结果在 completion 对象本身（与 OpenAI 示例一致）。
- 列表支持 `model`、`metadata[key]`、`after`、`limit`（1–100，默认 20）、`order`（默认 asc），
  返回 `first_id`/`last_id`/`has_more`；更新只允许 `metadata`。
- 流式请求在结束时重建 completion 并保存；工具调用保存 `tool_calls` 消息；
  多选保存全部 choices；中途失败/客户端断开不保存半截结果。
- TTL 默认 30 天、最多 2000 条，每小时清理。

### 3. Chat：usage 与截断改用 tiktoken

- 新增 `core/tokens.py`：`count_tokens` / `truncate_tokens`，`o200k_base` lazy singleton；
  加载失败时回退 `len//4`，不影响服务启动。
- `usage.prompt_tokens` / `completion_tokens` / `total_tokens` 与 details 全部来自 tokenizer；
  `max_tokens`/`max_completion_tokens`/`max_output_tokens` 用 `truncate_tokens` 精确截断到
  token 边界，`finish_reason: "length"`（Responses 为 `status: "incomplete"`）。
- 镜像构建时预下载 tokenizer（`TIKTOKEN_CACHE_DIR=/app/tiktoken-cache`），离线可用。
- 上游没有计费 token 数据，这是可解释的近似；文档明确写明边界。

### 4. Chat：参数不再静默忽略

- `modalities` 含 `audio` → 400 `param=modalities`；`audio` → 400 `param=audio`。
- `service_tier` 只接受 `auto`/`default`，回显 `default`；其余 400（上游没有分级队列）。
- `metadata` 按 OpenAI 边界校验（≤16 对、键 ≤64、值 ≤512 字符），原样回显。
- 每个 chunk 与最终 usage chunk 都带 `service_tier`；choice 带 `logprobs: null`；
  assistant message 默认补 `refusal`/`annotations`/`audio`。

### 5. Responses：对象面与语义对齐

- `_response_object` 增加 `access_programs`、`background`、`service_tier`、`conversation`、
  `max_tool_calls`、`top_logprobs`、`safety_identifier`、`prompt_cache_key`、`completed_at`；
  `usage.input_tokens_details.cache_write_tokens = 0`；`output_text` 带 `logprobs: []`。
- `previous_response_id` 续聊时**总是**剔除 stored system/developer，只有本轮 instructions
  生效；`/input_tokens` 同样处理。
- 创建时立即把 `in_progress` 快照落盘，进行中可 GET；取消后持久化 `cancelled`，
  后续 partial 流不会把它覆盖成 completed。
- `input_items` 默认 `order=desc`（OpenAI 默认）。
- 不可表达参数明确 400：`background`（上游轮次绑定 WebSocket，没有可恢复队列）、
  `conversation`、`top_logprobs`、非 `auto`/`default` 的 `service_tier`。
- `instructions` 接受字符串或 text item 列表。

### 6. Files / Images / Models

- Files：`expires_after`（JSON in multipart，1 小时–30 天）、`purpose` 枚举校验、
  列表返回 `first_id`/`last_id`/`has_more`；过期文件按 `expires_at` 或 TTL 清理。
- Images：响应回显 `background`/`output_format`/`size`/`quality`；`stream: true` 明确 400
  （上游一次画完整张图，没有 partial image）。
- Models：返回 `shutdown_date: null`；`DELETE` 自动 405（符合 OpenAI 无删除模型端点）。

## 保留的物理边界

- `temperature`/`top_p` 等采样参数上游不暴露，接受但忽略。
- `usage` 是 tokenizer 估算，不是上游计费数据。
- 视频 `edits`/`extensions`/`characters`、Responses `background`/`conversation`、
  音频输出、图片流式生成、`logprobs` 明确不支持（400/501）。
- 聊天内生成的图片/视频/文档仍以 Markdown 链接追加到文本，而不是独立的 `image` 内容项。

## 0.12.1 复核修复（code review + 上游探针）

对 0.12.0 做了一次完整复核（`code-review-excellence` + 独立 Explore 审计 + 真实
muse.ai Web 探针），修复了以下可本地修复的差异：

### 安全

- **多 Key 数据隔离**：Files、stored completions、Responses 链与图片任务都记录
  `owner` 并在 list/get/read/delete/previous_response_id/cancel 上校验；`admin`
  可见全部，`legacy` 可见升级前的无 owner 数据。

### 协议形状

- Responses SSE 每个事件都带 `event: <type>` 行；`GET /v1/responses/{id}?stream=true`
  重放完整事件序列（created → output → completed/incomplete/failed/cancelled），
  官方 SDK 的 `responses.retrieve(..., stream=True)` 可用；`starting_after` 生效。
- `function_call_output.output` 支持 text/image/file part 列表；`input_file.file_url`
  由网关抓取并内联；`input_items` 跳过 reasoning / hosted-search 输出项。
- Chat legacy `functions` 请求现在返回 legacy `message.function_call` +
  `finish_reason: "function_call"`（流式 `delta.function_call`）。
- `service_tier` 接受 OpenAI 全部合法值并回显实际 `default`；`prompt` 模板明确 400。
- 模型 DELETE 返回 404 `model_not_found`；Files/Videos 未知 `after` 游标返回 404。
- lifecycle 对象只在 completed/incomplete 时带 `usage`，其余为 `null`。
- JSON 模式不再把网关生成的媒体 Markdown 拼进 `content`。

### 校验与清理

- Chat：`n` 上限 128、`stop` 最多 4 条、`response_format` 类型校验、采样范围校验、
  `tool_choice` 指向未知函数时 400。
- Videos：非法 JSON/size 明确 400；seconds 错误信息与 1–60 的实际范围一致。
- Files：`expires_after` 真正参与 `prune()`，过期条目同时删除磁盘字节；
  索引裁剪/加载过期条目也会清理字节。
- Responses：删除进行中的响应会取消上游并加墓碑，turn 结束后不会复活。
- 媒体 URL 抓取失败转为 OpenAI 400，而不是 500；通用 500 信封补 `param: null`。

## 0.13.0 本地缺口补齐

### OpenAI Uploads API

- 新增 `POST /v1/uploads`（JSON：`bytes`/`filename`/`mime_type`/`purpose`/
  `expires_after`）、`POST /v1/uploads/{id}/parts`（multipart `data`）、
  `POST /v1/uploads/{id}/complete`（JSON `part_ids`/`md5`）与
  `POST /v1/uploads/{id}/cancel`。
- 每片最大 64 MiB、最多 128 片；完成时按 `part_ids` 顺序拼接，总字节必须与创建时
  声明的 `bytes` 完全一致，可选 `md5` 校验；成功后写入 `FileStore` 并返回普通
  `file` 对象，后续 `file_id` 引用与直接上传完全一致。
- Upload 本身 1 小时后过期；`cancel`/过期/完成后都会删除分片字节。数据落在
  `data/uploads.json` 与 `data/uploads/`，逻辑与多 Key owner 隔离一致。
- 官方 `openai` 3.51.0 的 `client.uploads.create/parts.create/complete/cancel`
  已通过 SDK 回归测试。

### 图片输出格式转码

- `output_format`（`png`/`jpeg`/`webp`）与 `output_compression`（0–100）现在真正
  参与输出：Pillow 在本地解码上游图片并按请求格式重新编码；jpeg/webp 应用质量，
  png 忽略压缩率。
- JPEG 没有 alpha，RGBA 会先铺白底再编码；`background=transparent` 与
  `output_format=jpeg` 明确 400，避免返回“透明”却已丢失 alpha 的图。
- 未请求格式时保持上游原格式；同步与 `"async": true` 任务共用同一转码路径。
- Pillow 进入基础依赖，生产镜像无需额外 extra；响应里的 `output_format` 回显实际格式。

全量：`pytest` **329 passed**，`ruff check .` 通过。

## 上游能力边界与入口（零差异所需）

这些不是网关实现遗漏，而是 2026-11-16 对 muse.ai Web/Noise 协议重新探针确认的
上游缺口。若要求与 OpenAI **逐字段零差异**，需要 Muse 提供下列入口：

| 能力 | 上游现状（证据） | 零差异所需入口 |
|---|---|---|
| 采样参数 | 222 个 Web JS chunk 中不存在 `temperature`/`top_p`/`topK`/`presence_penalty`/`frequency_penalty`；`GET /model` 只返回 `auto/auto`（context 350k）与 `available_models` 一项；`POST /chat/stream` 的 Web 请求体只有 `items/node_id/session_id/capabilities` | Muse 在 `chat.stream`/模型设置中增加 sampling 字段，并在 Web UI 暴露控制项 |
| 真实 token 用量 | `/usage on` 是聊天命令，开启后 Auto 模型的回复与 `message_done.metadata` 仍无 `input_tokens`/`output_tokens`；`/chat/history` 的 metadata 无 token 字段；420 条 Web RPC 路由中没有 usage/credits/token 端点；`GET /wallet` 只返回支付方式 | Muse 在 `message_done`/transcript metadata 中返回真实 usage，或提供 billing/usage HTTP 端点 |
| 视频编辑/扩展/角色 | Web RPC 路由表没有 video edit/extend/remix 端点（只有 avatar 视频）；Web 状态 `chat.supportsVideoFileRefIngestion=false`；协议 `VideoRequest` 只有 prompt/model/size/duration/first_frame | Muse 提供视频引用上传 + 编辑/扩展/角色 API，或允许 `chat.stream` 接收视频 file_ref |
| 图片流式生成 | `ImageRequest` 是一次性生成，无 partial-image 事件 | Muse 提供逐帧/partial image 流 |
| Responses background | 上游 turn 绑定启动它的 WebSocket，没有可恢复的服务端队列；本地只能做进程内任务（重启即丢） | Muse 提供可恢复的后台 turn 队列或 turn 续接接口 |

因此当前策略是：**能真实兑现的按 OpenAI 形状实现；不能兑现的明确 400/501 并记录
上游入口，不伪造字段或静默忽略**。`usage` 的 token 数是本地 `tiktoken o200k_base`
计数，`max_tokens` 的截断边界是精确的，但它不是 Muse 的计费口径。
