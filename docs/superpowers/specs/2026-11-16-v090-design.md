# 0.9.0 设计：让网关在异常路径上也像纯 API

日期：2026-11-16。基于 0.8.0（commit 41ae354）的第二次缺陷审计。上一轮解决的是
单账号并发；这一轮审计覆盖 API 表面（schema/信封/SSE/CORS）与驱动异常路径
（取消、断线、线程污染），共发现 9 个缺陷。

## 缺陷清单

| # | 缺陷 | 影响 | 严重度 |
|---|---|---|---|
| D1 | 上游轮次从不被取消：`client.cancel()` 是死代码。`cancel` 事件唯一的设置点在 chat 路由的生成器 `finally` 里，而那时驱动生成器已经被抛弃（延迟到 GC 才清理），消费循环不会再运行 | 客户端断开、首字超时换号、总超时、failover 时，孤儿轮次继续在原账号 VM 上跑完，烧算力和配额 | 高 |
| D2 | 中止的轮次污染线程：超时/取消后 `thread.last_seq` 停在旧值，孤儿轮次的事件继续追加；同一 hint 的下一个请求从旧 seq 订阅，会把孤儿轮次的 `message_start`/`text_append` 重放进自己的回复流 | 跨轮文本串扰 | 高 |
| D3 | 死订阅挂满超时：Noise WS 中途断开时 Subscription reader 退出，`wait_from` 永远返回空，`_consume` 以 0.5s 空转到 300s 总超时才报错 | 断线后请求挂 5 分钟才 failover | 高 |
| D4 | CORS 只放行 chrome-extension：浏览器端 OpenAI 客户端（Open WebUI / LobeChat web / LibreChat）预检直接失败 | "纯 API" 的核心卖点破洞 | 高 |
| D5 | 未处理异常返回 FastAPI 默认 `{"detail": "Internal Server Error"}`，不是 OpenAI 错误信封 | SDK 客户端报错难读 | 中 |
| D6 | `response_format`（json_object / json_schema）被静默忽略 | JSON 模式客户端拿到散文 | 中 |
| D7 | `stop` 序列被静默忽略 | 精确截断类用法失效 | 中 |
| D8 | 信封缺 `system_fingerprint` | 对齐 OpenAI 信封 | 低 |
| D9 | `n>1` 被静默忽略（永远只回 1 个 choice） | 自洽性/多候选用法失效 | 中 |

## 方案取舍

- **D1 取消的实现位置**：(a) 在 chat 路由把取消语义一路传下去——需要在每个生成器里
  包 try/finally，容易漏；(b) **驱动层统一兜底**——`chat_stream` 用 `except BaseException`
  包住轮次执行，凡未完成的轮次（`outcome.done` 为空且 ack 已发出）都 best-effort
  `client.cancel(session_id)`。选 (b)：一处实现覆盖断开、超时、failover、stop 截断
  四种来源；`gateway.chat_stream` 同时补上 `finally: await gen.aclose()` 让清理立即
  执行而不是等 GC。
- **D2 线程处理**：(a) 把 `last_seq` 推到当前最大——但孤儿轮次之后还会追加更高 seq 的
  事件，治标不治本；(b) **中止即弃线程**——未完成即退出时把线程从 `state.threads`
  移除并关闭订阅，下个请求重开线程重发全量历史。选 (b)，语义干净。
- **D4 CORS 范围**：(a) 全局放开 `*`——dashboard/admin 也暴露，过宽；(b) **按路径**：
  `/v1/*` 允许配置来源（新增 `MUSE2API_CORS_ORIGINS`，默认 `*`，对齐 api.openai.com
  的 `Access-Control-Allow-Origin: *`），其余路径维持 chrome-extension 正则。
- **D6 JSON 模式**：上游没有采样参数可控性，只能靠提示词执行 + 解析校验。非流式：
  注入 JSON 指令块，产出后剥围栏、`json.loads` 校验，失败按 planner 重试；流式：
  像 tool 路径一样缓冲后校验再放行。`json_schema` 把 schema 摘要进指令块。
- **D7 stop**：靠 D1 的新能力——网关监视累计文本，命中 stop 即截断并关闭流，
  驱动的 BaseException 兜底会取消上游轮次。非流式同样截断。
- **D9 n>1**：非流式用并发临时线程 gather 合并 `choices[]`；流式 n>1 返回 400
  （诚实报错优于静默忽略；OpenAI 流式多选极少用）。
- **"cancelled" 状态语义**：需要实测。若 `message_done.status == "cancelled"` 会被
  `_consume` 当成失败抛 UpstreamError 触发 failover，这对我们主动取消的场景是错的。
  实测后决定：把我们发起的取消视为正常结束（保留部分文本，不报错）。

## 变更面

1. `drivers/protocol/driver.py`：D1 兜底取消 + D2 弃线程 + D3 死订阅快速失败；
   `_consume` 把 "cancelled" 状态与失败状态区分。
2. `services/gateway.py`：驱动生成器即时 aclose。
3. `api/routes/chat.py`：D6/D7/D9 的参数执行；`system_fingerprint` 入信封。
4. `api/middleware.py` 或 `app.py`：路径域 CORS。
5. `app.py`：catch-all OpenAI 错误处理器。
6. `config.py`：`cors_origins`。
7. 测试：驱动异常路径（取消调用、弃线程、死订阅）、stop 截断、JSON 提取、n>1、
   CORS、500 信封。
8. E2E（真实 muse.ai）：断流后上游真的停了（配合探针证据）、JSON 模式、stop、
   n=3、CORS 预检、错误信封。

## 探针计划（先于实现）

- P1：`/chat/cancel` 是否真的停轮次；`message_done.status` 取消时是什么值；
  并行轮次互不误伤。
- P2：`delta.message_done` 是否带真实 token/usage 字段（若带则替换近似 usage）。
